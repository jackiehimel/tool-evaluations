# Findings — Cascade

One entry per observed limitation or surprise about the tool itself. Numbered, with the evidence ID. Plain sentences. Added to as things come up; referenced from SCORECARD.md and RECOMMENDATION.md at write-up. Setup mistakes by the evaluator are not findings; they live in SETUP-LOG.md and DECISIONS.md.

1. **Any drop into a trigger list dispatches immediately, and only the coding stage has a capacity gate.** When the feature card was dragged to Planning it passed through To Do, and the implementation trigger matched at once. The run was stopped only because the pipeline-capacity gate counted the story 3 card still sitting in In Review against the limit of one. The gate applies to the implementation agent alone; planning, splitting and backlog-manager are exempt by design (`src/triggers/shared/pipeline-capacity-gate.ts:10-24`). Without that coincidence, a coding job would have been queued on an un-planned feature card, and as stories 1 to 3 show, a worker follows within about ten seconds. The later drops into Doing and In Review are not trigger lists; the queue de-duplicates pending jobs per card but we found no path that cancels a scheduled job when the card leaves the list. E-010, E-006 to E-008, SETUP-LOG 21:45.

2. **The planner assumes a single-card flow and points the user at coding, not splitting.** The comment ending "move to TODO when ready to implement" is hard-wired in the planning prompt template (`src/agents/prompts/templates/planning.eta:112`). It assumes the next stage is implementation on the same card. Splitting is a separate column with its own agent that creates new story cards in the backlog list and must not touch the original description (splitting prompt, `WORK_ITEM_CREATE_CONTAINER_ID`). Nothing in the tool steers a planned card toward splitting; the operator has to know the column order. E-010, E-009.

3. **The plan did not stay inside the frozen file scope.** Step 5 of the plan edits `docs/architecture.md`, which the hidden acceptance checklist for row 4 does not allow. The plan is otherwise inside scope (`lib/`, `app/changelog/`, `tests/`). Whether the coding stage follows the plan or the story text decides the changed-files audit. E-010.

4. **Cascade has no Trello identity of its own; it acts as whoever's token it holds.** Every bot comment and every human drag on the feature card carry the same Trello member id, the token owner, which here is the evaluator. Two consequences: a customer cannot tell tool actions from that person's actions in the card history, and the router drops that person's own card comments as "self-authored" (loop prevention, `src/router/adapters/trello.ts:77-78`), so the token owner cannot converse with the agents through comments. E-010 identity check, appendix Sep 1 log 21:23.

5. **Stock commits are authored `Cascade Bot <bot@cascade.dev>`, hard-coded, and the hosting provider blocks previews for them.** The identity is set in `src/utils/repo.ts:58-59` with no configuration or environment override (E-002). Vercel marked the preview Blocked on all three quick-story PRs because that author is not a member of the hosting team, so no preview URL was issued and the merge state stayed unstable. It cannot be changed on the Cascade side without a source patch, which the Sep 1 attempt made and this evaluation reverted. A hosting-side project setting that lets non-member authors deploy was noted on Sep 1 but not exercised in this evaluation. E-006, E-007, E-008, appendix.

6. **The default model is incompatible with the default engine, and the getting-started guide does not say so.** `PROJECT_DEFAULTS` sets the model to `openrouter:google/gemini-3-flash-preview` and the engine to `claude-code` (`src/config/schema.ts:10,16`). The Claude Code engine rejects OpenRouter model ids, so a project created with no model set fails its first run with a boot error, which is exactly what happened on Sep 1. The guide calls Claude Code the default engine and lists the keys it needs, and recommends OpenRouter for the LLMist engine, but never says the default model must be changed for the default engine (`docs/getting-started.md:143,162-175`). Appendix Sep 1 log 22:21, BASELINE.md.

7. **There is no scheduled trigger of any kind.** Custom agents are well supported (YAML definition, CLI registration, capability allow-list, on-demand trigger by CLI, dashboard or board list), but every trigger is webhook-driven; the event catalog has pm, scm, alerting and internal categories only. A recurring read-only agent needs an external scheduler calling `runs trigger`. E-005.

8. **Enabling an agent through the CLI does not enable its triggers.** `agents create` makes the agent config; every trigger stays off until `projects trigger-set … --enable` is run per event. The dashboard's enable flow does both. The Sep 1 first attempt at story 1 failed on this, and the step 7 agent list showed seven agents with zero enabled triggers until the second command was run. E-009, appendix.

9. **A card leaves In Review only on merge or by hand, and In Review counts against the in-flight limit.** The default limit is one and counts To Do, Doing and In Review together. The tool moves a card to Done only from the PR-merged handler (`src/triggers/github/pr-merged.ts:96`). Any team that reviews before merging, or that does not merge quickly, finds the pipeline blocked after the first PR until someone moves the card. E-007 precondition, appendix Sep 1 capacity skip, SETUP-LOG 20:27.

10. **The dashboard cannot register webhooks against a tunnel.** The web UI derives the callback URL from the browser's own origin (`web/src/components/projects/integration-scm-tab.tsx:146`) unless `VITE_API_URL` was baked in at image build time (`Dockerfile.frontend:24`), which `setup.sh` and `docker-compose.yml` never set. From `http://localhost:3001` the callback would point at localhost. Webhooks had to be created with the CLI's `--callback-url`. Any local or self-hosted install behind a tunnel or reverse proxy hits this. Appendix Sep 1 log 108, source verified 2026-09-02.

11. **Workers run with permission prompts bypassed, and the router holds the Docker socket.** The Claude Code backend passes `permissionMode: 'bypassPermissions'` and relies on the capability-derived tool allow-list plus a hook that blocks `git push`, `gh pr create` and `gh pr merge` (`src/backends/claude-code/index.ts:319-322`, `src/backends/claude-code/hooks.ts:16-45`). The router container mounts `/var/run/docker.sock` to spawn workers (`docker-compose.yml`). Both are design choices to record in SECURITY.md rather than defects. E-005.

12. **Branch prefix was not honoured on the first quick story.** The project sets `feature/`; story 1 opened `fix/page-title-agent-portal`. Stories 2 and 3 used `feature/`. The prefix appears to be advisory to the agent, not enforced. E-006, appendix (same on Sep 1).

13. **The tool's own PR test plan can be narrower than what CI runs.** Story 1's PR body claimed typecheck, eslint on one file and the test run, but not lint over the repo or the build; stories 2 and 3 claimed all four. CI and the local reproduction passed each time, so this is a reporting gap, not a quality one. E-006 to E-008.

14. **Card-to-PR latency and cost scale with the change, on a single run each.** 56 s and $0.41 for one line; 78 s and $0.70 for a three-file component; 103 s and $1.34 for six files with a docs lookup; planning the feature took 155 s and $1.16. All single runs; no reliability claim. E-006 to E-008, E-010.

15. **The planner rewrites the card title, not only the description.** The feature card was created as "Changelog page" and the planning run renamed it to "Add Changelog page listing combined agent updates feed" at 01:47:29Z, two seconds before replacing the description. The original prompt text survives only in the card history. A customer who uses card titles as stable identifiers, or who searches the board by the name they gave, will not find it. E-010 (card export), SETUP-LOG 22:00.

16. **Auto-chain after splitting is gated by the same `auto` label that enables merging, so unattended feeding cannot be tested without also enabling merge.** The chain to backlog-manager runs only if the parent card carries the `auto` label and the mapping has `labels.auto` (`src/triggers/shared/splitting-auto-chain.ts:36-41`); otherwise it returns silently with no log line. That same label is what the PR-ready-to-merge handler checks before merging (`src/triggers/github/pr-ready-to-merge.ts:215`). Enabling the `internal:auto-chain` trigger alone does nothing. E-011.


17. **Backlog-manager's card-move trigger cannot fire from Trello.** Its `pm:status-changed` trigger is described as "Backlog / Merged Card Move", but the router's Trello adapter only passes card moves into the Splitting, Planning and To Do lists (`src/router/trello.ts:31-35`, called from `src/router/adapters/trello.ts:56`); everything else is dropped as "not processable" before any handler runs. A card re-filed into Backlog at 02:14:40Z produced exactly that log line and nothing else. With the `auto` label absent (finding 16) and the `merged` list unused under a no-merge flow, the only way left to run backlog-manager is the on-demand CLI or dashboard trigger. SETUP-LOG 22:14, E-011.

18. **The CI-passed review trigger needs Actions read on the implementer token, and the docs do not say so for fine-grained tokens.** Both review dispatch paths (the `check-suite-success` webhook handler and the worker's post-completion check) call the GitHub Actions workflow-runs API with the implementer token (`src/github/client.ts:386`, `src/triggers/shared/post-completion-review.ts:35`). With a fine-grained token that lacks the Actions permission the handler fails with a 403 on every check-suite event and no review is ever dispatched; the failure is logged as non-fatal and nothing is posted to the PR or card. The getting-started guide asks for `repo` scope "or fine-grained tokens" without listing the permissions a fine-grained token needs (`docs/getting-started.md:120`). Attribution is shared with the evaluation's token choice. E-013.

19. **Dependency resolution only sees mapped statuses, and the default mapping leaves Done unmapped.** Backlog-manager checks a story's declared dependencies against the pipeline snapshot, which is built from the mapped list keys. The evaluation's mapping (made on Sep 1 from the documented shape: backlog, todo, inProgress, inReview) has no `done` or `merged` key, so a dependency card moved to the board's Done list "was not found in TODO, IN PROGRESS, IN REVIEW, DONE, or MERGED" and both remaining stories were reported as Backlog Blocked with "manual intervention may be needed". `done` and `merged` are optional keys in the PM config type (`src/pm/lifecycle.ts:33-34`) and appear in one manifest example (`src/integrations/pm/trello/manifest.ts:144`), but nothing in setup asks for them and the tool's own lifecycle never moves a card to Done except on merge (finding 9). A team that closes stories without merging, or reviews before merging, needs to map Done by hand to keep the backlog flowing. E-012 (second run), SETUP-LOG 23:04.

20. **The "CI passed" review trigger can fire before CI has started.** The review dispatch on `check-suite-success` decides "all checks complete" from the check runs GitHub has registered for the head SHA at that moment (`src/triggers/github/check-suite-decision.ts:103-110`). On PR #30 the Vercel app's check suite concluded success three seconds after the PR opened, before the GitHub Actions run had created its check run, so the list had nothing incomplete and the review agent was dispatched with lint, typecheck, test and build still to run. When Actions finished a minute later, the legitimate success event was dropped by the per-PR-and-SHA dedup ("already claimed by another path"). The source comments describe the same race for CodeQL (an internal incident) and add a deferred re-check for the not-all-complete case, but not for the no-check-run-yet case. On PR #29 the same Vercel event arrived while an Actions run already existed, so the dispatch deferred correctly. Consequence: on repos with a fast third-party check app, the reviewer can approve or request changes on a PR whose CI later fails; the reviewer here re-ran the checks itself, which masked it. SETUP-LOG 2026-09-03T17:31:30-04:00, E-017.

21. **Review and respond-to-review chain with no human gate and no round cap, and the responder will change code to satisfy a reviewer.** `pr-review-submitted` from the reviewer persona dispatches respond-to-review immediately; the shared attempt gate (`src/triggers/shared/gates.ts:175`) is used only by the check-suite-failure (3) and conflict (2) handlers. On PR #30 the loop ran four review rounds and three response rounds in approximately 15 minutes wall-clock (21:31:30Z review dispatch to 21:46:16Z final approval) and 16.5 minutes summed tool runtime for $5.20 before the reviewer approved. The summed runtime is higher because overlapping runs each count their full duration. Round one reverted the whole feature rather than taking the reviewer's hold-or-draft option; rounds two and three, having found that the tool set has no command to edit a PR title or convert it to draft, wrote ten lines of comments into `lib/garage-content.ts` describing the PR's status ("the PR title/description … should be disregarded until a maintainer retitles/closes the PR"). The responder also edited the card's acceptance checklist (unticked four items) while the PR title, body and card position stayed as the implementation left them. The final approved PR does nothing the story asked for; its ten comment lines are an unrequested change (row 4 was scored on the first head). E-017, E-026, MATRIX row 6.

22. **Backlog-manager treats "card in Done" as "code on main", and the coder handles the gap inconsistently.** With the Done list mapped (D-26) the selection comment says the dependency "is now in DONE, so the required … module is available" (story 2) and "both already in DONE, so no blocking work remains" (story 3); it does not check whether the dependency's PR merged. Story 2's coder detected the unmerged dependency and stacked its PR on the dependency branch (E-016); story 3's coder detected the same thing, wrote it in the PR body, claimed to have "filed a friction report on the card" (no such comment exists) and opened against main anyway, which is what the reviewer then blocked. Same situation, two runs, two behaviours. E-016, E-017.

23. **A custom agent type cannot boot unless its definition carries an inline system prompt.** The worker resolves the system prompt from `templates/<agentType>.eta` inside its image unless `prompts.systemPrompt` is set on the definition (`src/agents/shared/modelResolution.ts:83-89`, `src/agents/prompts/index.ts:112-122`). The schema marks `systemPrompt` optional and the documented custom-agent example has only `taskPrompt`, so a definition written from the docs fails with `BootFailureError: plan resolution failed: ENOENT … repo-summary.eta` after the worker has already spent two minutes warming the TypeScript cache. The fix is one YAML field; nothing in the CLI or docs points to it. E-023.

24. **The PM completion check forces a checklist write, which pushes a read-only agent past "one comment".** With `hooks.finish.pm.requiresPMWrite: true` the Claude Code backend's completion check reports "Agent completed but no PM write (checklist creation) was recorded" even after a comment was posted, and forces a continuation turn; the agent then created a five-item checklist on the card to satisfy it (E-023, 00:03:13Z to 00:03:27Z, $0.05). A comment does not count as a PM write for this check. A maintenance agent that is meant to post one summary either drops the finish hook (and then Cascade cannot tell whether it did anything) or accepts an extra checklist per run. Both PM writes were within the granted `pm:write` capability. E-023.
