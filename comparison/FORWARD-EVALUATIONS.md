## Questions the recorded evidence should eventually answer

| Question | Evidence needed before making a claim |
|---|---|
| Can it help deliver a working prototype from a bounded customer specification? | Independently checked behavior, artifacts, run unit, intervention log, and actual costs. |
| Can it support reusable customer-facing agents or maintenance offerings? | An exercised relevant capability, operational constraints, security and ownership/licensing considerations. |
| Is it useful as part of a wider ADLC workflow? | Observed native handoffs and integration boundaries, or a clearly labeled composition. |
| Could it underpin a repeatable delivery or implementation service? | A concrete scenario and demonstrable benefits, with commercial assumptions separately identified. |

These are **offering-fit questions, not predetermined pass criteria or scores**. A specialist tool should not be marked as a failed end-to-end ADLC merely because it does not claim to be one. No single-trial or differently packaged run should be described as proving coding reliability, productivity gains, broad cost superiority, or production-readiness.

## Publication boundary

Only sanitized, approved findings and evidence are added here. Original customer documents, detailed confidential requirement contracts, internal evaluator instructions, agent definitions, privileged environment details, and demo-recording scripts stay outside GitHub. Where relevant, a published result can cite **sanitized requirement IDs and observable acceptance outcomes** without publishing the original customer material. A missing public artifact does not authorize filling it in from assumptions.
